**結論 (60 s 基準・n=1・所要秒未記録の結果に基づく。断定は弱い)**: 60 s 超の必要条件は「unit 830 が先行して実行され、そのあとに unit 880 が走る」こと。境界の 2 条件 (`0..829`+880 完走 / `0..830`+880 60 s 超) はいずれも n=1 で、60 s 付近の揺れは未検証。
- 830 を省くと (`0..829` + 880) 完走する。
- 830 を入れても 880 を外すと (`0..830` のみ) 完走する。
- `830,880` (前の unit を 0..829 から切り離す) では完走する。
よって、830 の実行で作られた状態が 880 の実行で問題を起こす。0..829 の状態は 830 の入力に影響するが、単独の 830 は `ok`/`oob` で正常終了する。
**未解決**: 830 が残す状態の中身 (どのメモリ・どの間接 call 先が効くか) は未特定。`skip880` (880 を飛ばす) の完走 (§4) は、880 が 60 s 超の唯一の原因候補であることを示すが、880 のどこで時間を使うかは未確認。

単独 `SV_ONLY` は OFF / ON とも 880 を `oob` と返すため、full sequence と一致しない (REPORT_860 の注意を再確認)。

- OFF: `ok 870 / miss 47 / halt0 7 / oob 16 / other 1 / noproc 1`

- ok→oob が 2 件 (17, 368) と ok→halt0 が 1 件 (158) あるため、M2p は既定 ON の候補としては回帰を含む。

「oob 増分の原因」(受入 3 の後半): oob の総数は 16→14 で減るが、内訳は ok→oob (17, 368) と oob→ok (477) などが混ざる。個々の unit が M2p のどの remap に依るかは未調査。
