## 1. 0x10d3a30 (受入 2)

関数 (91 B) の構造:

```
0x10d3a34  rax = [g1];  cmp dword [rax], 0x7fffffff; jne 0x10d3a53
0x10d3a43  rax = [g2];  cmp byte  [rax], 0;          jne 0x10d3a53
0x10d3a4f  eax = 0; ret                                   ; 書込み無しで戻る
0x10d3a53  call 0x10c7850; mov [g3], eax                   ; 結果を dword 変数へ
0x10d3a61  cmp dword [g4], 0; setle al; je 0x10d3a86      ; g4 <= 0 のとき
0x10d3a72  rcx = [[g5]+0xd0]; mov byte [rcx], 0x3f         ; gradeChar := '?' (0x3f)
```

- 書込みが起きる条件: 「`g1 != 0x7fffffff` または `byte [g2] != 0`」かつ「`0x10c7850` の戻り値を `g3` に格納した後、`dword [g4] <= 0`」。
  g1–g5 の意味は未確認 (推定: g1 は残日数の sentinel 系、g4 は期限の残日数)。
- 直接呼出し元 (3 件; `probe_786.py` の `calls_to`):
  - **0x10cf498** (`0x10c7cd0` 内): 直前に `cmp byte [g6], 0; je 0x10cf49d` があり、`byte [g6] != 0` のとき呼ぶ。`0x10c7cd0` は登録パーサなので、パース終盤の期限判定と推定 (未確認)。
  - **0x11fd457** (`0x11fc770` 内): `cmp dword [rbp+0x427c], 0; je 0x11fd448` の後、`dword [g7] != 0x7fffffff` のときに呼ぶ。戻り値が非 0 なら `0xbd68e0` を引数 0x2a で呼ぶ。
  - **0x11fe627** (`0x11fc770` 内): `call qword [rax+0x50]` の戻り値が非 0 で、`dword [g8] != 0x7fffffff` のときに呼ぶ。戻り値が非 0 なら同じく `0xbd68e0` (0x2a)。
- `0x11fc770` の直接の呼出し元は 3 件 (`0xc4dba0`・`0xd18130`・`0xed7c00` 内)。その先は未追跡。

## 2. 0x11cb000 (受入 2)

- 関数 (9,239 B) 内の gradeChar 書込み `0x11cd0c1` の直前は、`0x11cd09e: call 0x9636a0` の戻り値が `0x101` のとき (`cmp eax,0x101; jne 0x11cd0c1`) に通る経路。`0x9636a0` が何をするかは未確認。

- 結論: 0x11cb000 の発火条件は、上記の表を引く間接呼出しの特定 (子 issue) が無いと確定できない。

## 3. 0x10d50d0 のループ (受入 3・訂正)

関数 (612 B) の要旨:

1. 入口の一回限りガード: `sub dword [g9],1; cmp dword [g10],-1; jne 0x10d5321` (本 REPORT §3.4 の unit 初期化節と同型)。
2. 0x10d50fd の比較 (double `[g11]` と定数) で、一致すれば構築パス (0x10d511c〜0x10d52d4)、不一致なら直接 `0x10d52d9` へ。構築パスの各分岐の意味は未確認。
3. `0x10d52d9`: `mov ecx,1; call 0x409410` (`0x409410` は確保ルーチン) → 新しい領域を gradeChar 用に確保し、`[obj+0xd0] := 新ポインタ` (`0x10d52ed`)。
4. `mov byte [ptr], 0` (`0x10d52f4`) → **`0x10d52fc` から始まる count-up**: `ptr の byte を 1 増やす (0x10d52f9)` → `byte + 0xa == 0x4a` (つまり byte == 0x40) になるまで繰り返す。
5. 終了後に `xor ecx,ecx; call 0x10c7cd0` (cl=0) で登録パーサを **1 回** 呼ぶ。

**訂正**: 本 REPORT §8 の「gradeChar == 0x40 のときだけパーサを再実行する」は誤り。実際は次のとおり。

- 関数は毎回 gradeChar を新しい領域 (確保) に作り直し、0 から 0x40 まで count-up してから、パーサを 1 回呼ぶ。
- 「再実行」の条件分岐は無く、count-up の終了条件 (byte == 0x40) だけがある。count-up は必ず 0x40 で終わるので、関数を抜けた時点の gradeChar は常に `@` (0x40)。
- これは「ポインタ張り替え」(確保 → 新ポインタを `[obj+0xd0]` へ) の一例で、本 REPORT §3.2 の追跡形で見つかった `mov qword [rcx+0xd0], rax` (0x10d52ed) と同じ箇所。

**未確認**: 0x10d50d0 を呼ぶ経路。直接の call は 0 件。rip 相対参照も 0 件。唯一の参照は 826 エントリの関数ポインタ表 (`0x1378820`〜`0x137a1e8`) の **idx 660** (abs64 `0x1379cc0`)。表の先頭を指す参照は見つからなかった (§2 と同じ扱い)。
