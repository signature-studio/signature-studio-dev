#### 5.3.1 (a) の結果 (`hs_store_111c.py`・機械語のみ・再測定なし)

- 0x1321966 の比較入力 `[rbp+0x111c]` の値は `([rbp+0x1878] >> 16) & 0xffff` (`0x13217b4`〜`0x13217c3`)。`[rbp+0x1878]` は Dispatcher の第 4 引数 `r9` (Index) を `0x1318729` で保存した値で、範囲内の実書込みはこの 1 箇所だけ。
- `0x132178c` (その値を作る分岐の入口) への飛び込みは `0x1318abf: jmp 0x132178c` の 1 箇所だけ (走査 `0x1200000..0x1321000`。全域 `0x1000000..0x1400000` の jcc/jmp/call 走査でも同じ 3 命令)。
- `0xf5b190` は `[rsi]` (= `[rbp+0x111c]`) へ直接書かない。`mov rsi, r8` の後、`call 0x11d06e0` の引数 `r8` として渡し、`0x11d06e0` が `word ptr [rbx]` へ直接書く値は `0` だけ (`0x11d0710`・`0x11d0730`。ただし `0x11d06e0` が呼ぶ `0x11cf880`・`0x11c8ba0`・`0x11829e0` の書込みは未追跡)。
- 結論: 0x1321966 の比較入力は、Index の上位 16 bit (0 に潰される場合を含む)。基準 run は `r9=0` 固定のため入力は 0 になり、この格納を通る経路は実測 0/256 だった (0 になることの機械語上の確認は本節の範囲外)。受入 1 の『供給元の値』は Index の値域で決まる。Index の作り (呼出側) は未追跡。
- 限界: 直接の mov 形式だけを数える。間接書込み・`0x1200000` より前からの書込みは含まない。

#### 5.3.2 (b) Index (r9) の呼出側の候補列挙 (`hs_disp_r9src.py`・機械語のみ・再測定なし)

- `.text` 全体 (`0x1000000..0x1400000`) の `call qword ptr [reg+0x70]` は **202 件**。vtable slot 0 (Dispatcher) 以外の呼出しを含み得るため、呼出元の同定はできていない。
- 各候補の直前 64 命令 (線形窓) で `r9`/`r9d` を設定する命令があったのは **2 件**のみ。残り 200 件は窓内に設定が無く、呼出側の Index 作りは追えていない。
  - `0x1090dc4`: 直前 `0x1090da8 mov r9, [rbp+0x60]`。引数 `rcx=[rbp+0x48]`・`rdx=[rbp+0x50]`・`r8d=[rbp+0x5c]`。
  - `0x1090ff9`: 直前 `0x1090fe1 mov r9, [rbp+0x98]`。同じ形の引数。
- 上の 2 件の `[rbp+0x60]`・`[rbp+0x98]` の書込み元は未確定。関数先頭を近似で `0x1090010` と取ったが、`push rbp` 位置の探索が正しくなく、書込みは取れなかった。
- 結論: Index (r9) の作りは未確定。受入 1 の『供給元の値』は、この 2 件の呼出側と `[rbp+0x60]`・`[rbp+0x98]` の書込み元を追えるまで決まらない。
- 測定: 全 .text の線形走査 1 回で `real 1m4s`、rc=0、起動直後の load 0.89 (`uptime`)。`hs_store_111c.py` (機械語のみ) の出力は §5.3.1 と一致。

#### 5.3.3 (c) 2 件の呼出元関数の r9 元 (`hs_r9_locals.py`・機械語のみ)

- 再現コマンド: `FL_WIN64_DIR=<展開先の親> PYTHONPATH=<unicorn,pefile,capstone,tools/shared の site-packages> python3 hs_r9_locals.py` (`hostshim/` で実行。素材は `fl-win64` の `extracted/block00031_PE.bin`)
- 測定 commit: `f522fb030` (`hs_r9_locals.py` の `TARGETS` を `[rbp + 0x60]`・`[rbp + 0x98]` に絞った commit。以前の測定 commit `fa20228f7` の出力と差は無い)
- 測定 (`f522fb030`): `real 54.4 秒`、rc=0、起動直後の load 0.73 (`uptime`)。

- 2 件 (`0x1090dc4`・`0x1090ff9`) は同じ関数 `0x1090cb0` 内にある (先頭は `push rbp` の直前が `ret`/`int3`/`nop` のものを後方探索)。
- `0x1090cca mov [rbp+0x60], r9`: 関数入口の r9 (= この関数の呼出元が渡した Index) を保存する。よって `0x1090dc4` の `r9 = [rbp+0x60]` は、この関数の呼出元の Index に依る。
- `0x1090d0a mov qword ptr [rbp+0x98], 0`: `[rbp+0x98]` は 0 で初期化される。`0x1090ff9` の `r9 = [rbp+0x98]` はこの 0 を指すが、`0x1090f9d lea rcx, [rbp+0x98]` で `[rbp+0x98]` のアドレスが渡されるため、その先の呼出先が書き換え得る (未追跡)。
- `0x1090cb0` を直接 `call rel32` する箇所は `.text 0x1000000..0x1400000` に 0 件。呼出元は間接 call か、別形式の呼出し。ここで止まる。
- 結論: Index の作りは「関数入口の r9 (呼出元依存)」と「0 初期化の `[rbp+0x98]` (呼出先の書換えに依る)」の 2 経路に分かれた。どの経路が格納 `0x1321966` まで届くかは未確定。受入 1 は未達のまま。
- 測定: `hs_r9_locals.py` の `real 52.8 秒`、rc=0、起動直後の load 0.88 (`uptime`)。
