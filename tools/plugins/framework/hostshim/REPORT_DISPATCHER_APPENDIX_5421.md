#### 5.3.1 (a) の結果 (`hs_store_111c.py`・機械語のみ・再測定なし)

- 0x1321966 の比較入力 `[rbp+0x111c]` の値は `([rbp+0x1878] >> 16) & 0xffff` (`0x13217b4`〜`0x13217c3`)。`[rbp+0x1878]` は Dispatcher の第 4 引数 `r9` (Index) を `0x1318729` で保存した値で、範囲内の実書込みはこの 1 箇所だけ。
- `0x132178c` (その値を作る分岐の入口) への飛び込みは `0x1318abf: jmp 0x132178c` の 1 箇所だけ (走査 `0x1200000..0x1321000`。全域 `0x1000000..0x1400000` の jcc/jmp/call 走査でも同じ 3 命令)。
- `0xf5b190` は `[rsi]` (= `[rbp+0x111c]`) へ直接書かない。`mov rsi, r8` の後、`call 0x11d06e0` の引数 `r8` として渡し、`0x11d06e0` が `word ptr [rbx]` へ直接書く値は `0` だけ (`0x11d0710`・`0x11d0730`。ただし `0x11d06e0` が呼ぶ `0x11cf880`・`0x11c8ba0`・`0x11829e0` の書込みは未追跡)。
- 結論: 0x1321966 の比較入力は、Index の上位 16 bit (0 に潰される場合を含む)。基準 run は `r9=0` 固定のため入力は 0 になり、この格納を通る経路は実測 0/256 だった (0 になることの機械語上の確認は本節の範囲外)。受入 1 の『供給元の値』は Index の値域で決まる。Index の作り (呼出側) は未追跡。
- 限界: 直接の mov 形式だけを数える。間接書込み・`0x1200000` より前からの書込みは含まない。

#### 5.3.2 (b) Index (r9) の呼出側の候補列挙 (`hs_disp_r9src.py`・機械語のみ・再測定なし)

- `.text` 全体 (`0x1000000..0x1400000`) の `call qword ptr [reg+0x70]` は **202 件**。vtable slot 0 (Dispatcher) 以外の呼出しを含み得るため、呼出元の同定はできていない。
- 各候補の直前 64 命令 (線形窓) で `r9`/`r9d` を設定する命令があったのは **2 件**のみ。残り 200 件は窓内に設定が無く、呼出側の Index 作りは追えていない。
  - `0x1090dc4`: 直前 `0x1090da8 mov r9, [rbp+0x60]`。引数 `rcx=[rbp+0x48]`・`rdx=[rbp+0x50]`・`r8d=[rbp+0x5c]`。
  - `0x1090ff9`: 直前 `0x1090fe1 mov r9, [rbp+0x98]`。同じ形の引数。
- 上の 2 件の `[rbp+0x60]`・`[rbp+0x98]` の書込み元は未確定。関数先頭を近似で `0x1090010` と取ったが、`push rbp` 位置の探索が正しくなく、書込みは取れなかった。
- 結論: Index (r9) の作りは未確定。受入 1 の『供給元の値』は、この 2 件の呼出側と `[rbp+0x60]`・`[rbp+0x98]` の書込み元を追えるまで決まらない。
- 測定: 全 .text の線形走査 1 回で `real 1m4s`、rc=0、起動直後の load 0.89 (`uptime`)。`hs_store_111c.py` (機械語のみ) の出力は §5.3.1 と一致。

#### 5.3.3 (c) 2 件の呼出元関数の r9 元 (`hs_r9_locals.py`・機械語のみ)

- 再現コマンド: `FL_WIN64_DIR=<展開先の親> PYTHONPATH=<unicorn,pefile,capstone,tools/shared の site-packages> python3 hs_r9_locals.py` (`hostshim/` で実行。素材は `fl-win64` の `extracted/block00031_PE.bin`)

- 測定 (`f522fb030`): `real 54.4 秒`、rc=0、起動直後の load 0.73 (`uptime`)。

- 2 件 (`0x1090dc4`・`0x1090ff9`) は同じ関数 `0x1090cb0` 内にある (先頭は `push rbp` の直前が `ret`/`int3`/`nop` のものを後方探索)。
- `0x1090cca mov [rbp+0x60], r9`: 関数入口の r9 (= この関数の呼出元が渡した Index) を保存する。よって `0x1090dc4` の `r9 = [rbp+0x60]` は、この関数の呼出元の Index に依る。

- `0x1090cb0` を直接 `call rel32` する箇所は `.text 0x1000000..0x1400000` に 0 件。呼出元は間接 call か、別形式の呼出し。ここで止まる。
- 結論: Index の作りは「関数入口の r9 (呼出元依存)」と「0 初期化の `[rbp+0x98]` (呼出先の書換えに依る)」の 2 経路に分かれた。どの経路が格納 `0x1321966` まで届くかは未確定。受入 1 は未達のまま。
- 測定: `hs_r9_locals.py` の `real 52.8 秒`、rc=0、起動直後の load 0.88 (`uptime`)。

#### 5.4 0x41d110 の戻り値の源 (`hs_call_41d110.py`・`hs_call_41d110_sub.py`・`hs_call_41d110_glob.py`・機械語のみ)

- 格納 0x1321b6c の値 = 直前の `call 0x41d110` (0x1321b5b) の戻り値 + `0x12a8` (0x1321b60〜0x1321b68)。
- `0x41d110` の分岐 (VA 付き):
  - 0x41d114 `cmp byte [0x15ec2d8], 0` → 0 なら 0x41d14b: `rax = gs:[0x58]`、`rax = [rax + [0x13a9388]*8]` を返す (TLS スロット経路)。
  - 0x15ec2d8 ≠ 0 なら 0x41d123: `call 0x41cf60` (ecx = `[0x13a9388]`)。rax ≠ 0 なら返す。0 なら `call 0x41d000` の後、0x41d138 で同じ `call 0x41cf60`。rax ≠ 0 なら返す。0 なら 0x41d142 `rax = [0x15ec2d0]` を返す。
- `0x41cf60` は `jmp qword ptr [rip + 0x1554812]` 1 命令の間接 jmp。先の実体は**未解決** (IAT 系の参照先を解決していない)。
- `0x13a9388` (`.data`・PE 初期値 `0xffffffff`): 書込みは 0x41d066 の 1 箇所 (`mov [0x13a9388], eax`、eax = `call 0x41cf40` の戻り値)。その直前 0x41d05f の `je` は `lea rax,[0x32a8]` (定数・非 0) のため取られない。よって 0x41d050 が呼ばれると必ず書かれる。読みは 11 箇所 (0x41d010 ほか。`hs_call_41d110_glob.py`)。0x41d050 の直接呼出元は**未確認**。
- `0x15ec2d0` (`.bss`): 書込みは 0x41d07c の 1 箇所 (`mov [0x15ec2d0], rax`、rax = `0x41cf60` の戻り値)。読みは 0x41d142 の 1 箇所。
- `0x15ec2d8` (`.bss`・フラグ・PE 上は 0 初期化の領域): 読みは 0x41d114 の 1 箇所。書込みは 0x41d912 の 1 箇所 (`mov byte [0x15ec2d8], 1`)。この書込みは 0x41d8f0 の中で `r13d == 1` のときだけ (0x41d905 `jne 0x41d94d`)。0x41d8f0 は前 run の G18 (#4385 の `r9=1` 経路)。ただし本 run では実行しておらず、基準 run でフラグが立つかは再測定していない。
- 参照の数え方 (`hs_call_41d110_glob.py`): `.text` 0x401000..0x13a44b0 の全命令のメモリオペランドを capstone の access (READ/WRITE) で判定。rip 相対と絶対 disp32 の両方を含む。上の 3 グローバルの参照は各々 `0x15ec2d8` 2 件 (R 1・W 1)、`0x15ec2d0` 2 件 (W 1・R 1)、`0x13a9388` 12 件 (W 1・R 11)。旧版 (`mov` のみ) の『書込み 1 箇所』は全命令の走査でも変わらなかった。レジスタ経由の間接アクセスは含まない。
- 0x41d110 の直接呼出し: 走査範囲 0x1000000..0x1400000 で 52 件 (0x1321b5b と 0x1321b22 を含む)。この走査は `.text` 末尾 (0x13a44b0) の後の `.data` を含むが、呼出し形式の一致だけを数えた。0x401000..0x1000000 は走査していない。
- 実行記録 (commit `f1fe27e58`・HEAD 同一・`FL_WIN64_DIR` は `fl-win64` 展開先・load は起動直前の `/proc/loadavg`):
  - `hs_call_41d110_glob.py`: rc=0、`real 2m58.959s`、load 0.87。出力 sha256 `57b9bf0c…834bb`。
  - `hs_call_41d110.py`: rc=0、`real 0m41.100s`、load 1.01。直接呼出し 52 件 (節ごとに数えた)。
  - `hs_call_41d110_sub.py`: rc=0、`real 0m4.805s`、load 1.01。`byte [0x11cf1bd]` と `qword [0x11cf187]` は `.bss` 上の値で PE に実データが無く、`rd` が `None` を返す (表示上の `None`)。それ以外の `dword [0x13a9388]` 系は `0xffffffff`。

結論: 0x1321b6c の値は `0x41d110` の戻り値 + 0x12a8 で、戻り値は (a) フラグ 0 なら TLS スロット (中身は未確定)、(b) フラグ非 0 なら `0x41cf60` (間接 jmp・先は未解決) の戻り値か `[0x15ec2d0]` (その書込み元も `0x41cf60` の戻り値) のどれか。**供給元の値は未確定**のまま。確定 0 / 未確定 5 は変わらない。受入 2 は未実施。

#### 5.5 0x41cf60 の間接 jmp 先 (`hs_jmp_41cf60.py`・機械語と PE インポート表のみ)

- `0x41cf60` は `jmp qword ptr [rip + 0x1554812]` (`0x41cf60`〜`0x41cf65`) の 1 命令。スロット VA は `0x1971778`。
- スロットの PE 上の初期値は `0x1574002` (IAT のヒント/名前への参照)。PE インポート表で `0x1971778` を引くと `kernel32.dll!TlsGetValue` に一致。
- よって `0x41d110` の『フラグ非 0』経路の `call 0x41cf60` は **`TlsGetValue(ecx = [0x13a9388])`** の呼出し。戻り値はその時点の TLS 値で、実行時にしか決まらない (静的には未確定)。
- 実行記録 (測定 commit `1316c634b`・load は起動直前の `/proc/loadavg`): `hs_jmp_41cf60.py` rc=0、`real 0m9.669s`、load 0.51。

#### 5.6 0x41d050 の呼出元 (`hs_call_41d050.py`・機械語のみ)

- 0x41d050 は `sub rsp,0x28` で始まり、0x13a9388 へ `call 0x41cf40` の戻り値を書く関数 (§5.4)。
- 直接の参照を 4 形式で走査した。すべて 0 件:
  - `call`/`jmp` rel32 (`.text 0x1000000..0x1400000` の逆アセンブル・生バイト `E8`/`E9` の両方)
  - 絶対 32bit (`0x41d050` の 4 バイト) と RVA 32bit (`0x1d050`) の生バイト一致 (`0x400000..0x13a44b0`)
  - RIP 相対の `lea` (`.text` 全体の rip 相対オペランド 48,027 件)
- 検証: 同じ走査で `0x41d110` を指定すると 52 件 (§5.4 と一致)。走査器は動いている。
- 結論: 0x41d050 は、静的な直接参照 (call・jmp・アドレス即値・RVA・RIP 相対 lea) を持たない。呼出しは関数ポインタ表・間接 call (`call reg`/`call [mem]`) 経由と考えられるが、それを同定する手段は本節の範囲外。よって 0x13a9388 の書込み元 (0x41cf40 の戻り値) は未確定。
- 限界: 間接 call の経路は未追跡。`0x41d050` の到達は実行 (emulator) でしか示せない。
- 測定: `hs_call_41d050.py` の実行 1 回の記録: rc=0、real 57.5 秒、load 0.59 (実行直前の `uptime`)。
- 受入 1・2 は未達のまま。確定 0 / 未確定 5 は変わらない。
