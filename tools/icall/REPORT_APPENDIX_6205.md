# ICALL-128 (#6205): 関数 0xc589b0 の書込み元の静的追跡

素材: `fl-win64` の `block00031_PE.bin` (PE32+ DLL)。`objdump -d -M intel` の出力を読んだ (アドレスは `objdump -d` の表示 = VA。image base 0x400000 を含む。ファイル offset ではない)。実行による検証は行っていない (wine / box64 / qemu は runner に無い)。コード変更はなく、静的解析のみ。

## 2. 受入条件 2: 表 0x15e0ab0 と 0x390

- **表の実体**: `0x15e0ab0` は `.data` にあるポインタ変数で、ファイル上の初期値は `0x16b81b0`。この先は `.data` の外 (ファイルに中身が無い) なので、表の中身は実行時に作られるとみられる。要素は 8 バイトで `{int32 key; uint8 val}` (`c5bd74`: `cmp eax,[0x390]`, `c5bd93`: `byte[rax+rcx*8+4]` を読む)。要素数は指す先の手前 8 バイト (`c5bd1d`〜`c5bd49`: `[ptr-8]`、ループは `0..count-1`)。
- **表の初期化**: 本関数 (`0xc589b0`〜`0xc5d668`) には `[0x15e0ab0]` を書く命令が無い。表の初期化は本関数の外 (他の関数か loader) にあるとみられるが、箇所は未特定。
- **表への追記**: 本関数の `c5d144`〜`c5d163` で `0x417fc0` を呼んで要素を 1 つ伸ばし (汎用の container 操作とみられ、同名の呼出しは block 内で 1955 箇所あるため関数名の同定は未確定)、`c5d1aa`〜`c5d1b0` で key (`edx=[0x390]`) を書き、`c5d1f5`〜`c5d1fd` で val を書く。つまり **表はメモ化 (append only)** で、miss のときだけ追記する。
- **0x390 の由来**: `c5bd09` の定数 `0x425c4587` のみ (本関数内で他に書込み無し)。IEEE single では約 55.068。本関数が書く key は定数 `0x425c4587` のみ (他の関数が表へ書くかは未確認)。

## 3. 経路 (0x396 → 0x2cf → g22)

- `0x396` の書込みは 2 箇所 (`c5bd93`: 表引きの hit、`c5d111`: `0x377` の複写)。hit のときは `c5d111` を飛ばす (`c5bd99`→`c5d201`)。
- `0x377` の決まり (`c5bdf9` で 0 に初期化):
  - `0x353 == 0` → 0 のまま (`c5c5a7`→`c5d0d7`)。
  - `0x353 != 0`, `0x364 > 0`, `0x364 - 0x360 <= 0` → 1 (`c5c5cd`)。
  - 上記以外で `0x2ee != 0`, `0x364 != 0` → 2 (`c5d0b0`)。ただし `0x364 - 0x360 <= 0` なら 1 に戻す (`c5d0d0`)。
- `c5d202`: `0x2cf = (0x396 == 2)`。
- `c5d21a`: `[0x1504dd8] = 0x2cf` を書いた**直後**に `c5d220` で同じ値を読む。よって g22 の判定は今回の `0x2cf` で決まる。`g22 = 2` が書かれるのは `0x2cf == 0` (つまり `0x396 != 2`) のとき (`c5d248`)。

### 前回 REPORT (#6052 の停止報告) への補足

- `c5d21a` で `[0x1504dd8]` に `0x2cf` を書き、`c5d220` がその直後に同じ場所を読む。よって `g22=2` の判定は今回の呼出しの `0x2cf` で決まる。前回の「`[0x1504dd8]` の値を次の呼出しで引き継ぐ」は、この読み書きの向きを明記していなかった。呼出し間の引継ぎを示す箇所は確認できていない (`[0x1504dd8]` は両経路とも書いてから読んでいる)。
- 表 (`0x15e0ab0`) への書込みは miss 時の追記 (`c5d1aa`〜`c5d1fd`) だけで、hit のときは書かない。前回の「表引きが `0x396` を表へ書き戻す」の書戻しは、追記時の val 書込みを指す。
