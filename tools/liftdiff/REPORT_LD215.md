# liftdiff LD-215 (#4429) — 併存 20 関数の戻りレジスタを、分岐を越えた呼出し元・呼出し先の経路で判定

> 親 #4379 (LD-212) の子。前段 [`REPORT_LD212.md`](REPORT_LD212.md) は窓 24 命令の線形読みで止まった。
> 結論: **受入条件は未達**。判定を確定できたのは 20 関数のうち 1 件のみで、`targets/m11.json` の `ret_override` は変えていない。

## 1. 結論

- 判定器 `tests/ld215_retprop.py` は、呼出し元を分岐の両方向に辿り (`call`・間接 `jmp` で打ち切り)、rax / rdx / xmm0 の『読まれる』『上書き』『ret まで素通し (pass)』『未確定 (unknown)』を分類する。呼出し先は ret に至る全経路で must-def / may-def を求める。
- 併存 20 関数のうち、**呼出し元の全経路が決まり、かつ戻り候補が一意に決まったのは `6ed480` の 1 件だけ** (xmm0 が 3 呼出し元で `ucomisd` 等に読まれ、rax / rdx は読まれない)。
- ただし `6ed480` の型 (double か float か) は確定していない。呼出し元が読むのは `ucomisd` (比較) で、戻り型の証拠として弱い。LD-158 は同関数を『rax 書換えあり・区別不能』で対象外にしており、この判定はそれを覆す根拠として不十分。`ret_override` には入れない。
- 残り 19 関数は『未確定 (unknown)』か、呼出し先の経路が間接分岐で打ち切られ must-def を出せなかった。窓を越えても確定しない。

## 2. 方法 (再現)

- 入力: `FL_WIN64_DIR` の PE `extracted/block00031_PE.bin` (fl-win64 素材を `$RUNNER_TEMP/fl-win64` に展開)。
- スクリプト: `tests/ld215_retprop.py` (本 PR で追加)。
  - 呼出し元: E8 rel32 走査で call 命令を集め、target が一致したものだけを数える (LD-212 と同じ)。call 直後から最大 `--budget` (既定 400) 命令・経路数で打ち切る。`xor r,r` は読みから除外する。
  - 呼出し先: entry から全経路を辿り、ret 到達時点で書かれたレジスタの積 (must) と和 (may) を取る。呼出し先の `call` は clobber のみ (定義とは数えない)。
- 実行: `FL_WIN64_DIR=$RUNNER_TEMP/fl-win64 python3 tools/liftdiff/tests/ld215_retprop.py <PE> --tsv work/ld215_probe.tsv`。
- 所要時間: 実測 **0.38 秒** (load 0.3 秒・同じ素材で 2 回再現)。

- 列の意味: 読 = 戻り後に読まれた (候補)、上 = 戻り後に上書きされた、素 = ret まで素通し、未 = 窓・経路で決まらず。

- xmm0 は全関数で読まれる件数があるが、呼出し前の値を読んでいる可能性は残る (前段 §1 と同じ注意)。
- 呼出し先 must-def は、rax+rdx+xmm0 の 5 関数 (`442670` 等) で must に rax を含むなど、経路ごとの書込みが揃わないものが多い。`8e6660` の must に rax・rdx が入るのは、全経路で rax / rdx を書く (dead の 211 件と整合) ため。

## 4. 前段 (LD-212) との差

- 前段の窓 24 命令の読みでは「rax / rdx 読 0 件」。本 PR の経路追跡でも同じ。窓を広げただけでは戻りは決まらない。
- 追加で分かったのは、xmm0 が多くの関数で呼出し元の**比較・演算命令** (ucomisd・addsd・divsd・cvtsd2ss) に読まれること。これは戻り値の利用と読めるが、呼出し前の値の再利用も混じるため、型を確定する証拠にはならない。
