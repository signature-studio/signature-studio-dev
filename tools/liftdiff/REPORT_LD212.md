# liftdiff LD-212 (#4379) — 併存 20 関数の戻りレジスタを呼出し元の機械語で判定した結果

> 親 #3572 (LD-162) の子 (前段 [`REPORT_LD158.md`](REPORT_LD158.md) §3.1・§6)。
> 結論: **受入条件は未達**。呼出し元の読みでは rax / rdx / xmm0 のどれが戻り値かを確定できなかった。`targets/m11.json` の `ret_override` は変えていない。

## 1. 結論

- 併存 20 関数 (rax+rdx 6・rax+xmm0 3・rdx+xmm0 6・rax+rdx+xmm0 5) の E8 呼出し元は計 **240 件**。内訳は表 §3。`8e6660` が 310 件 (E8 走査の件数) で最多。
- 呼出し後の窓 (24 命令・call / jmp / ret で打ち切り) 内で **rax / rdx が『読まれた』呼出し元は、20 関数の全 240 件で 0 件** (表 §3 の rax r・rdx r 列が全て 0)。残りは『窓内で上書き (dead)』か『窓内で未確定 (unknown)』。
- 『読まれた』の大半は xmm0 (259 + 83 + … 件) だが、これは呼出し前の xmm0 を読んでいる可能性を含むため、戻り値の証拠にならない。
- 呼出し先の ret 直前 FP 命令 (§3.2) は、rax+xmm0 / rdx+xmm0 の関数で xmm0 への演算と読める (`7ce2e0` `ba05f0` 等)。ただし『rdx+xmm0』の関数では rdx を書く命令が ret 直前に無く、rdx を戻すかは判定できない。
- したがって 20 関数の戻り型は**確定しない**。`ret_override` の追加は行わない (誤った型を焼き込まない)。

## 2. 方法 (再現)

- 入力: `FL_WIN64_DIR` の PE `extracted/block00031_PE.bin` (fl-win64 素材)。
- スクリプト: `tests/ld212_retuse.py` (本 PR で追加)。
  - `tests/ld39_callsites.py` と同じ E8 rel32 走査で呼出し元を集め、capstone で 5 バイトの call として再デコードし、target が一致したものだけ数える。
  - 各呼出し元で、call 直後から最大 24 命令を線形に読み、rax / rdx / xmm0 (下位 64bit) の最初のアクセスを『read (読まれた)』『dead (上書きされた)』『unknown (窓内で決まらず)』に分類する。
  - `xor r,r` 等のゼロ化イディオムは『読み』から除外した (除外しないと rdx の read が水増しされる。初回実行で確認)。
  - 分岐の先は追わず、call / jmp / ret で打ち切る。
- 実行: `FL_WIN64_DIR=<展開先> python3 tools/liftdiff/tests/ld212_retuse.py <PE> --tsv work/ld212_retuse.tsv`。
- 測定 commit: 本 PR の commit (main `d97c2a609` の上にのみ、新規 `tests/ld212_retuse.py` と本 REPORT を追加)。所要時間 **0.26 秒** (load 無視できる)。
